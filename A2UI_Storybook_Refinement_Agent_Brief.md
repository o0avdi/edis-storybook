# Capstone: Storybook / A2UI Showcase Refinement

## Role and mission

Act as a senior React/Storybook engineer, developer-experience designer, and QA engineer. Refine an existing, functioning-but-unpolished standalone Storybook project into a showcase-ready, technically honest demonstration of A2UI Basic Catalog primitives, composition, and Storybook-to-A2UI export. Work in the actual local codebase, not a fresh rewrite. Inspect and run it first, make improvements incrementally, then validate with real browser screenshots and interactions. Do not stop at a passing compilation if the result still looks unfinished.

**Primary project:** the local `a2ui-basic-storybook` folder, originally created from `a2ui-basic-storybook.zip`.
**Exporter source:** https://github.com/o0avdi/a2ui-storybook-exporter, pinned by this project's `package.json` to commit `142dd7b4523ff3b37fabacd798b09fbc9de2dfdb`.
**Reference budget sample:** https://github.com/o0avdi/a2ui-showcase-demo/blob/feature/personal-budget-demo/server/providers/budget-sample.ts
**Reference renderer:** https://github.com/o0avdi/a2ui-showcase-demo/blob/feature/personal-budget-demo/src/a2ui/SurfaceView.tsx

Before changing code, read `README.md`, `docs/DEMO_WALKTHROUGH.md`, `package.json`, `.storybook/main.ts`, `.storybook/preview.ts`, `src/styles.css`, `src/basic/*`, `src/stories/*`, `src/examples/*`, `src/extensions/StatusBadge.tsx`, and `scripts/*`. Examine the screenshot examples the user has supplied where available. Confirm the real exporter CLI with `npx storybook-a2ui --help`. Preserve pinned dependency versions unless a change is necessary and explained.

## Nonnegotiable architectural distinctions

1. **Use the official A2UI SDK Basic Catalog and actual SDK renderer implementations** for the basic gallery. Do not replace them with lookalike React versions.
2. The **budget dashboard is a composition** of primitives through an A2UI `createSurface` message, not a React `BudgetDashboard` or a new per-business-use component library. The sample is deterministic, not live AI. Preserve its working actions and bindings.
3. The A2UI Basic Catalog from `basicCatalog.toJson()` is **SDK-authored**, not generated by our Storybook exporter. Label its provenance clearly everywhere.
4. Our **storybook-a2ui exporter** reads Storybook component metadata and produces an additional A2UI component schema. It cannot reconstruct all SDK Basic Catalog semantics or correctly infer all events, child slots, arrays, and functions from wrapper props. Do not claim otherwise, fabricate successful export reports, or quietly discard fields to make a demo pass.
5. Export new, genuinely reusable, **primitive** React components with documented flat scalar/enum props. Do not change the existing exporter code, specification, validation, or default strict behavior just to inflate compatibility. If a bug appears, document it with a reproducer before changing source.

## Priority A: Make the Storybook experience polished and informative

The current `src/stories/BasicPrimitives.stories.tsx` sets `component: BasicSurface` for all primitives; `BasicSurface` accepts `message: unknown` and `onAction?: ...`, so every story displays the same generic, unhelpful Controls panel. Fix the Storybook experience without misrepresenting SDK component contracts:

- Each primitive story should expose **its meaningful user-level controls**. Examples: Text (`text`, `variant`); Button (`label`, `variant`, and a working event); Slider (`label`, `min`, `max`, `value`, `steps`); TextField (`label`, `value`, `placeholder`, `variant`); CheckBox (`label`, `checked`); ChoicePicker (`label`, `options`/selected state where practical); DateTimeInput (`label`, date/time toggles); Row/Column (`justify`, `align`, example content). Organize story-specific preview args and metadata explicitly rather than expecting the Storybook manifest to discover SDK schemas through a generic harness.
- Hide `message`, `onAction`, and raw internal data structures from the public Controls panel and Docs presentation. Keep the core SDK renderer harness internal.
- Use Storybook's built-in **Actions** integration and `fn()` for event callbacks where possible; clicking the actual SDK Button should log to the native Actions panel (not only to a JSON block under the preview). Maintain useful SDK action payloads and no-op-safe behavior.
- Show appropriate value changes/state for interactive controls using the SDK's data-model bindings. Demonstrate that a slider, checkbox, or text field genuinely works, not just that its initial value appears.
- Add a few purposeful, named variants for key primitives: Button styles, Text variants, input states, and basic layouts; avoid excessive redundant stories.
- Use Storybook Docs with concise descriptions, controls, schema/usage notes, and linked examples. Distinguish **preview-level controls** from the actual official A2UI catalog schema. Avoid making the preview wrappers look like exportable source components.
- Fix layout, typography, spacing, preview containers, background, and whitespace. Use official SDK theme/CSS customizations, not wholesale component reimplementations. The current screenshot shows a tiny budget tracker at the left of a huge blank area: make it legible on a 1920x1080 projection and at a smaller laptop viewport. Make components feel intentionally framed, not floating at the top-left. Consider 16px+ body text and a sensible max width.
- Refine `src/basic/BasicCatalogExplorer.tsx`: searchable component list, neat property summary/table (required, type, description, defaults), syntax-highlighted or readable JSON view, copy JSON action, clear count and schema provenance, no horizontal-scroll-first presentation. Preserve access to raw official JSON.
- Improve the navigation hierarchy to support a 2-minute live demo: start / official components / composed example / exporter. Avoid over-decorating with distracting animations and unrelated visual effects.

## Priority B: Strong, honest exporter demonstration

Current `scripts/export-extension.mjs` exports only `StatusBadge`. Keep that working. Add two or three small **non-composed** React primitives with genuine Storybook docgen metadata, e.g. `MetricLabel` (string + number), `ProgressIndicator` (numeric values + enum), or another clearly useful atomic building block. Keep prop types within what the real exporter supports: strings, numbers, booleans, string-literal unions; avoid callbacks, `children`, arrays, objects, reserved `id` / `component` prop names, unsupported defaults. Favor simple source, accessibility, and readability.

Required outputs:
- `storybook-static/manifests/components.json` — produced by Storybook, NOT manually authored.
- A verified, **multi-component exporter-generated** `catalog.json` and `export-report.json` for the new primitives.
- A one-component exporter-generated catalog for a clean live command.
- The official SDK Basic Catalog JSON as a **separate, labeled reference** artifact. The full official catalog and full exported extension catalog must never be conflated.
- A concise component-schema viewing command/script or browsable page so a presenter can show the JSON for one exported component, then the complete generated extension catalog and official Basic Catalog. Pre-generate deterministic copies for a reliable fallback and clearly label them as pre-generated.

CLI design:
- Preserve a real developer-facing `storybook-a2ui export` invocation and display the actual command used.
- Keep the demo without `--unmapped-events omit`; do not invent `--supported-subset` if the pinned CLI does not support it. Prefer strict default export for genuinely compatible components.
- Required flags `--storybook`, `--catalog-id`, and `--out` are legitimate. Optionally add a small convenience npm script that calls the real CLI, prints the underlying command, and ensures a clean output directory. Do not suppress meaningful errors or silently skip invalid components.
- Support running Storybook in one terminal while another terminal builds/exports. A static Storybook build is needed for the manifest even if the dev server is running. Prebuild before the live demo to avoid prolonged compile output.
- Preserve reproducible `npm ci`/lockfile and an easy PowerShell-oriented demo walkthrough.

## Priority C: Visual/browser quality assurance

Run the project locally using the package manager specified by the repo and Node 24 where practical. Use Playwright or an equivalent browser automation tool to actually open the Storybook UI and inspect:

- The start page and Basic Catalog explorer.
- Text, Button, Slider, TextField, CheckBox, Row/Column, and at least two other primitive stories.
- Storybook Controls for each (no generic `message: unknown` / raw callback properties).
- Storybook **Actions** after an actual button click, and observable changes to interactive bound values.
- The budget composition at 1920x1080 and 1280x800, including changing categories/editing amounts and toggling the JSON view.
- The generated extension catalog and report.

Capture screenshots before and after. Fix clipping, overlapping, tiny font, excessive whitespace, horizontal-scroll problems, and console errors. Do not fake a passing test, fake a generated schema, or represent sample data as a model inference. If an SDK theme constraint prevents a requested visual effect, explain it and choose a practical styling alternative.

Test gates:
1. `npm run typecheck` passes.
2. `npm run build-storybook` passes and writes official `index.json` and `manifests/components.json`.
3. Exporter `inspect` runs and strict export succeeds for selected new primitives.
4. The generated catalog validates against the pinned A2UI v1.0 schemas; inspection report says what was exported and blocked.
5. All interactive demos render and respond correctly without uncaught console errors.
6. At least one end-to-end UI test demonstrates a Storybook action appearing in Actions, and interactive controls changing the preview; provide screenshots.
7. Output/provenance is clearly documented in README / demo walkthrough.

## Workflow constraints

- Make changes on a new Git branch, e.g. `feat/storybook-demo-polish`. Do not overwrite `main` or modify the original showcase application.
- Favor small, maintainable React/TypeScript modules and descriptive, honest docs over new dependencies or a UI framework rewrite.
- Read the installed SDK API and types when unsure instead of guessing; verify the exact Storybook version syntax.
- Work in two phases: (1) make Storybook examples genuinely usable and visually polished, (2) make the export path reliable and ready to present. Finish both, then provide a short demo script, commands, diffs, verification logs, and screenshots.
- If some scope proves impractical, retain working parts and clearly identify the blocker instead of claiming completion.

## Definition of done

A first-time visitor can click through the official Basic Catalog primitives and immediately understand their useful properties and interactions. A Button click clearly appears in native Storybook Actions. The budget tracker is readable and interactive and transparently generated from `createSurface` JSON rather than a prebuilt dashboard. A developer can run one clean exporter command, see a genuine validated schema for a primitive, and examine both a generated multi-component extension catalog and the distinct official Basic Catalog.

**Out of scope for this pass:** recording/editing a showcase video, changing the core exporter architecture, implementing agent live inference inside Storybook, or redesigning the separate A2UI showcase app.
